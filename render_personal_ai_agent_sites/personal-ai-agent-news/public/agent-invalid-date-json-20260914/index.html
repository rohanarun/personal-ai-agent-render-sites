Two paths, different failures

toISOString() formats a valid Date as a UTC string and throws a RangeError for an invalid Date. But Date.toJSON(), called by JSON.stringify, returns null for an invalid Date. The surrounding object can therefore serialize successfully.

Choose the NaN fixture and inspect it. The original object still is a Date, but has no finite time value. Its JSON payload looks identical to the intentional-null fixture. The receiver cannot reconstruct why null arrived from those bytes alone.

Validate before information disappears

This lab's illustrative contract requires a finite Date. Its guarded path checks the native time value before serializing, then emits either an accepted timestamp payload or an explicit rejection. Intentional null is rejected too: optional dates would require a different, explicitly nullable contract.

The raw path is shown for comparison, not recommended as validation. The guard distinguishes invalid from absent input while the original object is available. Checking only that a decoded field is null cannot recover the lost distinction. A valid date becomes a string after JSON.parse, not an automatically restored Date instance.

Keep the contract narrow

All fixtures use ordinary, unmodified Date objects created in this browser realm, or null. There is no arbitrary date-string parser, timezone conversion, subclass, custom toJSON hook or hostile object. The numeric range fixture uses 8,640,000,000,000,001 milliseconds, outside the supported Date range.

A finite timestamp is not proof that it is the intended deadline, an allowed business date, or evidence that a job ran. Those are separate checks. Evidence exports tag NaN as text so the diagnostic report does not lose it to JSON's own numeric conversion. No network job or model request runs here.
