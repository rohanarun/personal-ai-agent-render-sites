Good timeout behavior

Recovery is a policy, not an instinct.

Retry only with slack

A retry is sensible when the remaining window can absorb another attempt and its setup cost.

Narrow the objective

When the full task will not fit, reduce scope to a reversible, useful partial result and label it.

Stop with evidence

Return the timeout, attempted work, and next safe action so a later run does not repeat the same guess.

This is a teaching simulation, not a production timeout policy. It demonstrates bounded recovery and explicit state: a tool failure should change the next action, not disappear inside a generic retry loop.
