Stream Reader Handoff

A streaming agent changes consumers before the next chunk arrives. Releasing ownership and cancelling production are different operations.

Ready.

    A rejected read is not a cancelled stream

    The first reader asks for data while the queue is empty. Releasing its lock rejects that read with a TypeError. The producer remains available: the next step enqueues the string "chunk-A", and a newly acquired reader receives it.

    const first = stream.getReader();
const pending = first.read();
// Attach rejection handling before releasing.
first.releaseLock();
controller.enqueue('chunk-A');
const second = stream.getReader();
const result = await second.read();

    Each step uses native ReadableStream operations. The underlying source's cancel callback is counted separately. No network or model request is involved.

    What the trace proves

    Unread chunks remain available after a lock release. Here a chunk is produced after release, then consumed by the new reader. A pending read belongs to the old reader and does not silently migrate. The rejection handler is attached before release so the expected TypeError is handled.

    Once the second read succeeds, this demo closes the source and releases the second reader. Close is intentional normal completion, not cancellation. The visible cancel count should remain zero throughout this sequence.

    An agent stream consumer should decide whether it is handing off ownership, abandoning the stream, or finishing normally. A catch block that treats every rejected read as a producer failure loses that distinction. Reset creates a fresh source and ignores stale callbacks; it is not a remote-task cancellation mechanism.
