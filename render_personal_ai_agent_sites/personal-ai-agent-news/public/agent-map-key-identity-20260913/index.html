Same fields. Different key.

An in-memory agent cache keyed by objects follows object identity, not a deep comparison of request fields. Observe the native Map behavior.

original = { task: "summarize" }
alias = original
fresh = { ...original }
cache.set(original, "result for summarize")

Identity can surprise an agent cache
Original and alias point to the same object. Fresh is a new object, even when its fields match. Map can therefore find the first two keys but not the third.
Mutating original changes the fields visible through alias. The Map entry remains associated with that object, so its old result remains available. That is correct Map behavior, but a poor cache contract if the result depends on the changed task.
Choose the cache contract deliberately
Illustrative agent scenario: a request object is reused for a different task. An identity-keyed memoizer may still return the previous answer. In contrast, rebuilding an equivalent request object may miss the cache. Neither observation proves semantic equivalence or freshness.
A production cache needs an explicit definition of what makes requests interchangeable: relevant inputs, versions, scope and invalidation. A JSON string is not automatically a universal semantic key. This lab is not Super's computer-use cache and does not model its matching or verification.
Export boundary
The export stores field snapshots and lookup booleans. JSON does not preserve the live reference relationships shown here. Reloading that report cannot reconstruct these exact in-memory object identities.
