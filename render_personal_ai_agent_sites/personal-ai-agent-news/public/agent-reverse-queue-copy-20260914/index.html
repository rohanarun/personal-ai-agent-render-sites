Reverse the view or the queue?

Changing presentation order should be an explicit choice about ownership.

One operation mutates, one copies
reverse changes the source array in place and returns that same array. A second call reverses the source again. toReversed returns a new array while preserving the source order. This lab always reverses the source, not the previous result, so repeated copying produces the same order until the source changes.
The comparison uses three ordinary task objects, A, B and C. The blocks show their order and completion flag. They are illustrative task records; no real work is started, retried or marked complete outside this page.
A new array is not new tasks
After either operation, toggle the first result task. Both arrays refer to that same task object, so its done flag changes wherever that object appears. The copied array owns a different sequence of references, not independent copies of the referenced objects.
In an agent dashboard, a reversed presentation list may need independent ordering while still reflecting the same task state. In an isolated experiment, sharing those objects may be unwanted. Choose the ownership model deliberately instead of treating every copy as deep isolation.
Inspect identity, not just matching text
The status reports source === result and the location of the result's first object in the source. Those are runtime reference checks. The downloaded JSON contains value snapshots plus explicit identity observations; JSON by itself does not preserve shared references.
Changing modes resets the fixture to avoid mixing histories. Actions are capped at 30 until reset. This lesson covers dense arrays of plain objects, not sparse slots, proxies or custom accessors. Copying here is not a general concurrency-safety guarantee.
