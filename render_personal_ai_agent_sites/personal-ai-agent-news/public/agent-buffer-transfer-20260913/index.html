Copy bytes or transfer ownership?

An agent pipeline may pass binary data between execution contexts. A copy and a transfer leave the sender in different states.

Source

Destination

Hexadecimal bytes. Increment wraps after FF. Reset creates a fresh eight-byte buffer and clears the destination.
Try the copy path
Clone, then increment the first source byte. The destination retains its previous value. Ordinary ArrayBuffer cloning makes a separate buffer in this example.
Try the ownership path
Reset, then transfer. The destination receives the bytes, while the source's byteLength becomes zero because it is detached. The source mutation and handoff controls are disabled until reset. This does not mean the original payload was eight zero bytes.
What an agent engineer should take away
Illustrative scenario: a coordinator hands a binary payload to a worker. Code that expects to reuse the sender's buffer after a transfer needs a different ownership plan. A fresh source allocation is not recovery of a detached object.
This page calls structuredClone in one browser context. It does not launch a worker, send a network message, measure throughput or prove a zero-copy implementation. It demonstrates observable buffer semantics, not an agent framework.
SharedArrayBuffer, concurrent access, unsupported object types and error recovery are separate topics. A transfer is not a durable checkpoint or a security boundary.
