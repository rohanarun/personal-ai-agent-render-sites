A failure-recovery simulator

After a failed tool call, retrying is a decision.

A timeout does not tell an agent whether the action happened. Explore how side-effect risk and verification quality change the authority to retry, verify, or ask for help.

Retry authority is restricted.

When a side effect may already have happened and there is no reliable receipt, repeating the call can turn uncertainty into duplication.

Current state: unresolved outcome
RetryRepeat only when the action is safely idempotent or the outcome is known not to have occurred.
VerifyQuery an authoritative status before producing another side effect.
AskReturn the decision when neither retry nor verification can be trusted.
Recommended posture: verify the provider status before doing anything twice.

Retries need a proof, not a mood.

An agent should not treat a timeout as permission. It should classify what may have happened, seek the narrowest authoritative evidence, and preserve the user's trust when the system cannot establish a clean boundary.

Idempotency is evidence

A retry is safer when the operation has a stable idempotency key and the receiver guarantees deduplication.

Verification beats optimism

A read from the system of record can convert “unknown” into a known state without creating another effect.

Escalate with a useful question

When the agent cannot prove the outcome, ask for the missing fact or hand off with the exact attempted action and uncertainty intact.
