Dagu vs Super Powers AI

Compare an explicit workflow engine with assistant-driven computer-use workflows. Decide who owns each step, then test the failure path.

Published by Super Powers AI. Reviewed September 14, 2026. Documentation comparison, not a hands-on benchmark or independent ranking.

Where Dagu fits

Dagu describes a local-first engine for declarative YAML around existing commands and tools, with schedules, retries, human tasks, logs and a Web UI. Its documented actions include shell commands, containers, SSH and HTTP. This is a strong candidate when a team wants to own executable workflow definitions and their runtime. That fit assessment is an inference from the official overview.

Dagu is not limited to non-AI jobs. Its built-in MCP server lets authenticated clients inspect state, edit workflow definitions and control runs. An AI client can operate the engine; this is not evidence that every desktop interaction is a built-in Dagu capability.

Where Super fits

Super presents an assistant with its own apps and computer-use workflows. Its inspected backend implements verified procedure caching. Evaluate it when your task involves assistant-led work across a supported computer surface, particularly repeatable procedures. Confirm the exact app and account support in a pilot at Super Powers AI.

A cached workflow is not a scheduler, a durable retry contract or proof of a completed run. Neither product wins every task. A team may retain Dagu for explicit job orchestration and assess Super for a separate interaction stage; this page does not claim a prebuilt integration between them.

Retry scope matters more than a check mark

Dagu documents step retries within the same DAG attempt and root-level DAG retries that create a new attempt and require the scheduler. Manual retries are a separate surface. Test which side effects repeat before enabling retries for a publishing or update step. See Dagu's retry semantics.

For Super, the inspected workflow cache requires an owner, verified-complete confirmation, task or source context and runnable Python steps. Portability checks can decline storage. A lookup may return a workflow with helper-version and verification evidence, or a miss when no safe match is available. Caller handling is still needed on a miss, and matching can incur model usage.

Procedure reuse can avoid reconstructing eligible steps. Source inspection and this product footage do not establish measured speedups, universal compatibility or live cache availability for your account. Ask for evidence of both a successful reuse and a safe miss on the actual workflow.

Separate license cost from operating cost

As reviewed, Dagu lists free Community self-hosting, Team at $50/month for 3 server licenses or $500/year, and Pro at $150/month for 15 or $1,500/year. Workers are not separately licensed. Community permits up to two API keys; paid plans add controls including SSO and audit logging. These are Dagu license terms, not an all-inclusive compute or model bill. Check the current pricing and plan comparison before purchase.

No like-for-like Super cost or performance ranking is asserted here. Record actual usage, plan terms, infrastructure and operator time for the same bounded task before drawing that conclusion.

Start with Dagu when owning YAML, command execution and a self-hosted operations boundary is the requirement. Trial Super when assistant-driven interaction is the requirement. Treat those as starting hypotheses, not rankings. Keep approval and output verification explicit whichever runtime executes the work.
