An empty match can stall.

A successful match is not proof that a parser moved forward. Compare four bounded exec calls with a complete matchAll scan over the same text.

Success without movement

The empty pattern succeeds immediately. For this pattern, exec returns an empty string and leaves lastIndex at zero. Four calls therefore report the same position. The lab deliberately stops at four calls; it never runs an unbounded while loop.

matchAll has its own empty-match advancement behavior. It moves forward and eventually finishes. With Unicode mode enabled, this fixture produces indices 0, 1, 3 and 4. Without it, index 2 is also visited inside the supplementary character's surrogate pair.

Offsets are still UTF-16

U+10400 occupies two UTF-16 code units. The full input is four code units long. Unicode-aware advancement skips the interior position, but reported indices are still string offsets, not counts of user-perceived characters or model tokens.

MDN's exec reference warns about empty-match loops. The ECMAScript iterator algorithm specifies advancement after an empty match. This page uses native RegExp and String.matchAll, not a predicted trace.

A parser needs a progress contract

For an illustrative agent-log parser, a loop that counts every successful match as progress can repeatedly process the same span. Track positions as well as success. Prefer an iteration API whose behavior matches your task, or explicitly design and test advancement when managing a cursor yourself.

Blindly adding one to an offset is not a universal Unicode fix. This fixture contrasts two modes for one pattern and one short string; it does not implement a grapheme segmenter, a token parser or a general regex safety checker. It does not test catastrophic backtracking.

Both scans start with fresh expressions. matchAll uses its own iterator state; the export also records the original expression's lastIndex after scanning, which stays zero here. It should not be mistaken for the iterator's final internal cursor.
