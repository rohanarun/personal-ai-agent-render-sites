Enumerable does not mean serialized
The experiment creates ["job-A", "job-B"], then assigns a named property with your string value. That property is an own enumerable property: Object.keys sees it. But ordinary array JSON uses indexed elements from zero through length minus one. Extra named properties are ignored.
The key "01" is deliberately different from "1". It is not the canonical array-index spelling, so it adds metadata rather than replacing the second job. The offered property names do not change the array's length.
The alternative constructs a plain object with items and metadata fields. Its metadata object has an explicit property, so this string survives native stringify and parse. Empty string is still a present value. This lab uses no replacer, custom toJSON, prototype modifications or simulated serializer.
Make the receiving contract explicit
For an agent batch, place routing labels, correlation IDs and schema versions in agreed object fields rather than decorating an array. The receiving code must expect that envelope: changing a bare array to an object can break an existing API.
A round trip here proves representation retention only. It does not validate the label, authorize an action, deliver a message or prove the jobs completed. Validate the parsed shape and required metadata at the boundary; do not use a pre-serialization console display as evidence of what crossed it.
