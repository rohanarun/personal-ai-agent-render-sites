Same characters, different contract
In a replacement string, $& inserts the match, $$ inserts a dollar, and the prefix/suffix tokens insert surrounding source text. A callback's returned string does not expand those tokens. Here the search is a string, not a regular expression: only its first occurrence is replaced, and $1 has no capture group to reference.
Illustrative task: a text-editing agent is asked to insert the literal marker [$&] into a draft. The string path interprets it; the callback path returns it verbatim. Neither path proves that the edit was requested or that the surrounding draft is correct. Compare the result to the intended change before persisting it.
Separate matching from insertion
Changing how replacement text is supplied does not change where the first match occurs. An empty search inserts at the beginning; an absent search leaves the source unchanged. This experiment does not execute a user regex or replace every occurrence.
At a tool boundary, label the field as literal insertion text or as an intentional replacement template. Treat that as part of the tool's schema, not something a downstream step should guess from dollar signs. The download preserves all three inputs and both outputs for a reproducible local test. No file is edited and no agent is invoked.
