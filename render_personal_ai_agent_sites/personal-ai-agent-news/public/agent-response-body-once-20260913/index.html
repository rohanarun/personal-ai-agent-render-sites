Who consumed the response?

Reading a response for logging can leave nothing for the next consumer. Try the native browser operations and inspect the resulting state.

Observed operations
Local Response object with an illustrative body. No fetch, model call, or external tool runs. Reads use text(), not JSON parsing.
Try both paths
First read the original twice. The second read fails. Then start a new response, clone it before reading, and read both branches. Finally try cloning after consuming the original.
A Response body is a stream. Consumption disturbs it, and a used body cannot simply be read again. Cloning must happen while the body is usable. This page records native errors; exact error wording can differ between browsers.
Agent middleware example
Illustrative integration: diagnostic middleware reads a tool response to log its text, then passes the same Response to a parser. The parser's later read can fail because the body was already consumed. For small bounded payloads, one approach is to read once and explicitly pass the resulting text to later stages.
Cloning is not a universal free-copy solution. It splits the body stream, and uneven consumption can require buffering. This tiny fixed body does not measure memory behavior for large or unbounded streams.
State is not permission
bodyUsed reports consumption, not whether the response is trustworthy or successful. A locked stream can also be unusable even before that flag turns true. This lab does not acquire a stream reader, test HTTP status handling, or validate the body's contents.
