These are manually controlled native promises, not real provider calls. No model, network request, timer-based latency measurement or cancellation is involved.
Try a failure before a success
Reject call B, then fulfill call A. Race keeps B's rejection; any returns A's value. Race follows the first settlement, whether fulfillment or rejection. Any waits for a fulfillment unless all inputs reject.
All failures, and no calls
Reject C, B, then A. Any rejects with an AggregateError whose errors follow input order A, B, C, not rejection order. With empty input, any rejects while race remains pending.
The other work still exists
After a winner, the remaining buttons still settle their promises. Neither combinator cancels them. A fulfilled promise is not proof of a correct agent answer; validation and cancellation require separate application behavior.

Choose the request contract
A fallback system should say whether a failure ends the request, whether another result is still useful, and how remaining work is stopped or accounted for. This lab isolates settlement behavior; it does not measure accuracy, reliability or cost.
