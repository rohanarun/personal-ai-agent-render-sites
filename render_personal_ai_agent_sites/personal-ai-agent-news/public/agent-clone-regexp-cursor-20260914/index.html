Cloned RegExp Cursor

A scanner has already consumed one match. Does cloning its regular expression preserve where it will search next?

    Pattern is not progress
    The native structured-clone algorithm supports RegExp objects, but it does not preserve their lastIndex. The new object's pattern and flags describe what to find; its reset cursor says where the next global search begins.
    const scanner = /job-\d/g;
scanner.exec('job-1 job-2 job-3');
// scanner.lastIndex is now 5
const copied = structuredClone(scanner);
// copied.lastIndex is 0
    After scanning the original once, clone it, then scan both. The original finds job-2 while the clone finds job-1. They are separate objects: advancing one does not advance the other. Cloning again replaces the displayed clone with another fresh clone of the original.
    A handoff needs an explicit checkpoint
    An agent that delegates incremental text scanning should carry its input identity and intended offset explicitly. A cloned matcher alone is not a checkpoint. Restoring a cursor without confirming that the input and matching policy are unchanged can skip or repeat work.
    This experiment uses one fixed, bounded pattern with the global flag. When a search fails at the end, native exec resets lastIndex to zero; the next scan can start over. The trace exposes before and after offsets rather than interpreting zero as proof that no work happened.
    JSON exports describe pattern, flags and cursor explicitly. They do not serialize a live RegExp object. Thirty actions are allowed before reset. All matching and cloning occur locally with native browser APIs.
