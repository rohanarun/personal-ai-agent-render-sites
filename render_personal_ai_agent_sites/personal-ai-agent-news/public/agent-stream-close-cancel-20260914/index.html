Drain or discard

A streaming agent can stop producing without throwing away its queued output. Closing and canceling are different decisions.

Finish writing, then drain
Enqueue two chunks, close the source, then read three times. The first two reads return the queued chunks. The final read reports done. Closing prevents new chunks but does not remove the ones already waiting. No source cancellation callback is required for this normal finish.
Stop consuming, discard the rest
Reset, enqueue two chunks, then cancel the reader. The unread chunks disappear, and the source's cancel callback records the reason. Reading afterward reports done without delivering those chunks. Already delivered values are not undone.
A read on an empty, open stream stays pending. Enqueue a chunk to satisfy it, or close or cancel to finish it. The desk permits one pending read at a time. It tracks enqueues and read results to draw the unread list; it does not inspect a hidden browser queue. At most eight unread chunks can be queued in this demonstration.
Apply the distinction carefully
For an illustrative agent response, graceful completion can mean draining the output already produced. A user abandoning the response can mean they no longer want unread output. Choose that policy explicitly; do not label discarded output as delivered.
The native stream here has a manual source, not a network connection or a model. Its cancellation callback is evidence that this source was notified, not proof that an external service stopped work, reversed an action or refunded usage. In a real source, resource cleanup is part of the source implementation.
The JSON download preserves the current state, unread list, delivered values and event trace. Reset starts a new stream and clears the old trace. No model or remote API is called.
