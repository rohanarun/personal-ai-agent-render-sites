Message Port Startup Lab

A listener can exist while delivery is still disabled. Send a few messages, then start the receiving port.

The listener and the queue
A MessageChannel has two connected ports. Here, port1 posts a small object and port2 records each message event. With addEventListener, the receiver needs start() to enable delivery. Setting onmessage enables it implicitly.
Send three messages in the default mode. They remain unobserved by the handler. Start the receiver and watch them arrive asynchronously. Starting it does not synchronously call the handler inside the click; message events are delivered later. Switch to the property mode on a fresh channel and send again.
Do not confuse posted with processed
The posted count records successful postMessage calls in this fixture. The received count records handler observations. Their difference is not a measurement of the browser's internal queue, a dropped-message count, or evidence that a downstream task finished. An agent protocol needs its own completion acknowledgement when processing matters.
The trace contains sequence IDs, the receiver setup, and whether this page enabled delivery. It contains no real agent work. Both ports live in this page; no iframe, worker, network service or model is running. The experiment uses native browser messaging, not a timer-based imitation.
Reset is a new connection
Changing setup or choosing New channel closes both old ports, clears observations, and creates a new pair. Old messages are not migrated to the replacement. A generation check also prevents a late callback from an old fixture entering the new trace.
Up to 20 messages can be posted per fixture to keep the view bounded. This is a page limit, not a MessageChannel limit. Export captures the observations at the time you click, so an export made before delivery may contain fewer received IDs. There is no persistence across reloads and no claim of durable messaging.
