An Interval Does Not Await Your Job

A polling agent can start another async job before the previous one settles. These local jobs wait on promises that you release manually, making overlap observable without calling a server.

    The promise is not the timer's completion signal
    In interval mode, an async callback reaches its await and returns a promise. The timer does not use that promise to delay the next invocation. The JavaScript callbacks are not running CPU instructions simultaneously; their asynchronous work is in flight at the same time.
    Compare the two runs
    Start the interval run and leave all jobs pending. Once three starts are observed, the run stops admitting work but those jobs remain pending. Reset, choose the completion policy, and wait: only the first job starts until you complete it. The next timeout is scheduled after that completion, so this run keeps at most one job in flight.
    Stopping starts is not canceling work
    Stop future starts clears the timer and disables further scheduling. Jobs that have already started still need completion. Reset is different: this demonstration discards the run and releases its local promises without recording them as successful completions. Neither operation sends a cancellation request to a remote service.
    Choose the invariant, then the policy
    Illustrative task: a monitor refreshes a document summary. If a refresh must finish before another begins, completion-based scheduling fits that invariant. If independent jobs may overlap, an interval can be appropriate, but bound admission and verify how results are ordered. This toy does not implement errors, retries, distributed locks or crash recovery.
    The displayed timestamps use performance.now relative to the start click. They show this browser's observed sequence. Background throttling and other work can delay callbacks; the requested delay is not a deadline or a throughput promise.
