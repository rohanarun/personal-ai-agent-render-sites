Two separate contracts
The promise executor runs synchronously during construction. Calling resolve with this fixture's plain string settles the promise, but does not stop the function. In the first case, the after-resolve marker is recorded before a later throw. The promise remains fulfilled.
Returning after resolve exits the executor before that marker. Throwing before resolution instead produces a rejected promise. Both handlers are attached immediately in this lab, so the rejection is collected rather than left unhandled.
Read the order
Executor messages precede the "constructor returned" marker. The fulfillment or rejection handler runs later. This is why code after a completion callback can still change local state before the consumer's handler sees the result.
The visible after-resolve marker is a local trace entry, not an external side effect. A real wrapper might have cleanup or other work there. Place control-flow boundaries deliberately; fulfillment does not certify that no later executor code ran.
Do not generalize past the fixture
The Promise constructor documentation explains executor timing and settlement. Here resolve receives a plain string, not another promise or thenable. Resolution with another asynchronous value can adopt its eventual outcome; see the linked assimilation lab for that separate behavior.
The throw occurs inside the executor itself. A throw in a later timer callback is outside that constructor call and is not automatically converted into this promise's rejection. This lab does not schedule such a throw.
For agent integrations, a fulfilled wrapper is only the wrapper's chosen result. It does not prove a browser action succeeded, a server persisted data or an unrelated asynchronous operation stopped. Verify the intended output independently.
