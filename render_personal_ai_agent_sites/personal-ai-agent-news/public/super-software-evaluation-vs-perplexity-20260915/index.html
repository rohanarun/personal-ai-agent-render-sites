The deliverable is an evidence ledger

Suppose a twelve-person agency needs a project-management tool. Everyone wants a short list, but the expensive mistakes are usually hidden inside broad claims: “SSO,” “export,” or “guest access.” Those words do not establish which plan includes the feature, what data it covers, or whether it works with your setup.

A useful evaluation produces one row per requirement: the exact pass condition, source and date, eligible plan, observed trial result, and unresolved question. An AI report can locate a claim. A successful test can establish a narrower fact. Neither should silently turn into the other.

Our recommendation: start with two plausible vendors and three non-negotiable requirements. Resolve blockers before comparing nice-to-have features. This is a proposed workflow, not a measured head-to-head benchmark or an automatic procurement service.

Three claims that need a second question

Fictional examples below illustrate how to write a test. They are not claims about Super, Perplexity or any project-management vendor.

“SSO supported”

Requirement: employees authenticate through the agency's SAML identity provider on the plan being purchased.

Insufficient evidence: a feature page lists Google sign-in. A social-login button alone does not establish the required SAML configuration.

Next check: obtain the plan-specific SAML setup documentation and configure a disposable test account with an administrator. Record successful sign-in and the behavior after access is revoked, including any documented session delay.

Current verdict: unverified. Do not mark a pass from the word “SSO.”

“Export your projects”

Requirement: export task descriptions, comments and attachments with enough structure to reconnect each attachment to its task.

Insufficient evidence: a CSV export exists, but the documentation only describes task titles and dates.

Next check: create two dummy tasks with comments and attachments, export them, then inspect every required field and file. Record omissions and test the intended import destination if migration is a requirement.

Current verdict: unverified. A download succeeding is not proof of a complete migration.

“Collaborate with guests”

Requirement: an external client can review one project without seeing another client's project.

Insufficient evidence: the marketing page says guests are supported without specifying permissions or seat billing.

Next check: use a separate test guest account, confirm permitted access, and attempt the deliberately forbidden project URL. Check how that exact guest role affects the quoted bill.

Current verdict: unverified. Invitation delivery does not prove isolation or price.

Run the same pilot before choosing an assistant

  1. Define the decision. Name the two vendors, intended plan, number and type of users, three mandatory requirements, budget boundary and decision owner. Use dummy data rather than client records.
  2. Collect claims. Request official documentation URLs, retrieval dates, exact plan scope and short supporting passages. Missing evidence stays “unknown”; a search snippet is not a completed check.
  3. Separate research from access. Review the ledger first. Only authorize a specific trial action when the account, permissions and permitted changes are clear. Do not allow purchases, external invitations or production changes by default.
  4. Run the tests. The human evaluator owns the trial verdict. Save observations, files and exceptions. A vendor statement and a tested observation should remain separate columns even when they agree.
  5. Decide from blockers. A failed mandatory requirement rules a candidate out unless the owner explicitly changes that requirement. Unknown means more investigation, not a zero score hidden inside an average.

Compare the assistants on accepted evidence rows, unsupported assertions, manual corrections and total pilot spend. Do not compare only the time to the first answer. No such measurements have been collected for this article.

What the computer-use cache actually changes

Super publishes an open-source OpenAI-compatible cache proxy. Its documented mechanism stores eligible successful responses and reuses them for matching canonical requests; misses go upstream. This is inspectable technology, not a claim that every browser task costs nothing.

For vendor research, freshness is essential. An unchanged prompt asking for “current pricing” can match an old request. Include fresh source content in the actual request context or bypass caching; a date added only to metadata is insufficient because metadata is excluded from the default key. TTL limits entry age but does not certify the vendor page has not changed.

A cache hit avoids an upstream model call. It does not fetch a fresh page, execute a trial, certify a permission boundary or eliminate browser and infrastructure costs. The pinned proxy source makes that narrower mechanism inspectable; it is not a benchmark of the entire Super platform.
