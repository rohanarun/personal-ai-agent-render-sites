Binding is retained
Function.bind creates a wrapper with a receiver and optional leading arguments. Calling that wrapper with call does not replace its bound receiver. Binding it again also leaves the first receiver in place; new bound arguments follow the earlier ones.
Binding the original function instead produces a separate wrapper for B. In this fixture, arguments record where they entered the chain: "first", "second", and "live". The displayed array comes from the native invocation, not a predicted answer.
This example uses ordinary function calls. Constructor calls with new and arrow functions have different receiver rules and are outside the fixture. See the Function.bind reference.
Routing is more than a label
Imagine a local agent adapter keeps a callback created during initialization. Later, another part of the application passes a different context when invoking it. A changed variable name or call-site label does not prove the callback now belongs to that context.
Before wiring such an adapter to external actions, inspect the actual callback construction and test the receiving object. This lab appends only to local arrays. The A and B names are illustrative, not accounts, permissions or real agents.
Binding the original to B is a technical option shown here, not authorization to move a task. A production handoff still needs the intended owner, allowed action, and completion evidence. Changing a receiver cannot establish any of those by itself.
Trace boundaries
Each run creates new receiver objects and one fresh base function. The chart counts the local trace entries, while the export records their exact arguments. Switching the invocation clears old evidence; reset preserves the selected mode. Nothing persists across a reload.
No browser task, network request or model call is performed. This is a JavaScript behavior test, not a test of distributed routing or an agent product. Published September 14, 2026 by Super Powers AI.
