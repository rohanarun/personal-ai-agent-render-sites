Abort Reason Lab

A cancellation request is a persistent signal, not a rewind button.

One controller

One listener starts attached. Attach more before or after aborting. Repeated abort calls act on the same controller until reset.

Signal state

Observed events
    Three experiments
    Before cancellation: check throwIfAborted. It returns without throwing. Attach another listener, then abort. Both attached listeners observe the event.
    After cancellation: change the reason and abort again. The original reason remains. Attach a late listener: registering it does not replay the old event. Check the persistent aborted state when joining an existing operation.
    At a checkpoint: call throwIfAborted after cancellation. It throws the stored reason, which in this example is a string rather than an Error object. A fresh controller starts a separate uncanceled signal.
    What this means for agents
    An agent can pass a signal to an operation that supports cancellation, or check it before a step. This page only exercises the native signal: it makes no network request and does not demonstrate stopping a remote tool.
    A completed side effect stays completed unless a separate compensating action exists. Record which steps actually finished; do not label them rolled back merely because a signal is aborted. Also avoid assuming every rejection has an Error-shaped name or message.
    The trace is local browser evidence, not a distributed cancellation guarantee. Reset discards the local trace; export it first to retain the experiment.
