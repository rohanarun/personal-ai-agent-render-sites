Numeric years are not always literal

A date can be valid and still be the wrong century. Run two native JavaScript paths for January 1 at midnight UTC, then compare the actual year each produces.

Date.UTC

setUTCFullYear
The axis runs from year 0 to the largest displayed year, at least 2000. Both paths explicitly use UTC. No locale parsing, time-zone conversion or model request is involved.


The 99-to-100 discontinuity
Date.UTC(y, 0, 1) interprets numeric years 0 through 99 as 1900 through 1999. For year 100, that special mapping stops. The first path wraps the returned millisecond timestamp in a Date so that its ISO representation can be inspected.
The second path starts from new Date(0), then calls setUTCFullYear(y, 0, 1). That setter uses the supplied full year without the 1900 offset. January 1 and the epoch's midnight UTC time are explicit, so an existing month or local offset cannot explain the difference.
Leading zeros do not survive numeric conversion
A numeric year of 0024 is just the number 24. This form reads a number, not an ISO date string. Zero-padding a display does not alter Date.UTC's numeric-year rule. This experiment does not test arbitrary string parsing.
Year zero is a calendar convention
The JavaScript date model uses a proleptic Gregorian calendar with astronomical year numbering. A database or historical source may use another convention. Establish that convention before translating a year label; this tool does not interpret historical eras.


What an agent should validate
Illustrative scenario: an agent imports a catalog record with full year 24. A valid timestamp alone is insufficient evidence of a faithful import: the first path produces year 1924. Compare the resulting UTC year, month and day against the intended components before accepting a conversion.
If a source says only "24" and means a two-digit modern year, neither path can infer the intended century. Define that rule with the data owner. Do not silently choose the modern date simply because it looks plausible.
The lab deliberately fixes month and day and accepts integer years 0 through 9999. It is not a general date validator, scheduler or import service. Its JSON export contains the requested year, native timestamps, actual years and ISO strings, so the discrepancy can become a small reproducible test.
