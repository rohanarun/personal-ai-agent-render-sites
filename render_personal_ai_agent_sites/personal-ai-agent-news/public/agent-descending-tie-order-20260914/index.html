Descending without reversing ties

The scores agree. The next task may not.

Four illustrative tasks arrive A, B, C, D. Two native sorting pipelines put higher scores first, but only one preserves arrival order among equal scores.

Descending comparator

[...tasks].sort((a, b) => b.score - a.score)

Ascending, then reverse

[...tasks].sort((a, b) => a.score - b.score).reverse()

A tie is still a decision

Imagine a tool-dispatch batch where equally scored tasks should retain admission order. Reversing the ascending result changes that policy: a later equal-score task moves ahead of an earlier one. The descending comparator returns zero for equal scores, letting stable sorting preserve their original relative order.

When every score is different, the two rankings match. That can hide the issue in tests. An all-equal batch exposes it immediately. The values here are illustrative priorities, not model confidence estimates.

Be explicit about the contract

Stable sorting preserves the order in its input array, not a global wall-clock arrival guarantee. If batches are assembled differently, their ties can differ. For a reproducible distributed ranking, preserve an agreed sequence key and apply it as a secondary comparator.

(a, b) => (b.score - a.score) || (a.sequence - b.sequence)

That example assumes validated finite scores and suitable numeric sequence values. This experiment restricts scores to integers from -100 to 100, including zero and negatives; blank or invalid input blocks export. No claim is made about an invalid comparator, missing records or concurrent queues.

Native behavior, separate copies

Both pipelines sort shallow array copies. The original task sequence remains A, B, C, D. The experiment exports the input and both observed output orders, not a predicted result. It makes no agent or model request.

Reference: MDN Array.sort, including stable sorting and comparator behavior. The line crossings compare ranks, not runtime or performance.
