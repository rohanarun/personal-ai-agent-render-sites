Read and remove

takeRecords() returns the observer's pending mutation records and empties that queue. Without it, the callback receives this fixture's three child-list records after the synchronous code completes. With it, the immediate read receives those records and the callback receives none of those same records.

Reading the queue does not undo the mutations. All three nodes remain visible in either mode. A second immediate takeRecords call is included in the trace and returns an empty list because no new mutation occurred between the reads.

Delivery is not observation setup

A fresh MutationObserver is attached before each run's mutations. The fixture performs three separate appendChild operations while childList observation is enabled. It does not observe attributes, text changes inside descendants or the rest of the page.

The status is finalized in a later timer task, after the observer has had a delivery opportunity. This is an ordering demonstration, not a latency benchmark. Controls are disabled during the run, and the observer is disconnected after the result is captured.

For agent evidence collection

If instrumentation mixes manual queue draining and callback-based logging, it should retain the drained records in its evidence stream. Otherwise a missing callback can be misread as "nothing changed." Conversely, a mutation record only proves a DOM operation was observed; it does not prove a save succeeded on a server.

MutationRecord objects reference nodes. This lab snapshots their added and removed node text into ordinary JSON at collection time. That export is a bounded description of this run, not a live DOM reference or a complete page history. Real node contents could change later.

No model, network request or external app action occurs. The three labels are illustrative. Changing the mode or resetting clears the fixture and previous trace outside observation. Export always describes only the latest completed run.
