Maybe Memory

An agent wants to avoid revisiting a document. A Bloom filter can rule out a prior visit, but a positive answer means only maybe. Build the memory and find a collision.

64 bits, three addresses

Teal = set bit. Pink outline = the current query's addresses. Numbers are bit addresses, not stored document IDs.

Exact teaching ledger

One missing bit is enough

Insertion sets the key's addresses to one. Lookup checks the same addresses: any zero proves absence; all ones permit a false positive. With insertion only and consistent hashing, an inserted key cannot become a false negative.

Why an agent must verify a match

In this hypothetical document workflow, treating a positive as proof of a prior visit can skip new material. Use the filter as a preliminary test, then consult an exact store when it says maybe. The separate ledger here exposes that distinction; it is not part of the 64-bit filter.

Hashing and collisions

This experiment uses browser SHA-256 on each UTF-8 ID. The first three big-endian 32-bit words, modulo 64, choose addresses. Addresses can repeat. IDs are case-sensitive; surrounding whitespace is removed. The collision search tests up to 2,000 absent probe IDs and reports failure honestly if none match.

What the memory size excludes

The 64 bits describe the logical filter, not JavaScript memory consumption. The ledger, strings, and interface consume additional space. Reset clears everything. Individual deletion is unavailable because clearing shared bits could erase another key's evidence.
