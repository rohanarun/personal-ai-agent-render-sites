A retry has a credible recovery signal and enough remaining budget. Change the attempt, then record what made it different.

Persistence is not the same as progress.

An agent that retries after every error can look determined while doing the same thing repeatedly. That is dangerous when a tool has side effects, a user is waiting, or an external system is returning a durable rejection. A good retry policy asks what changed before it asks whether to try again.

This lab turns that question into four visible signals. Failure likelihood and side-effect cost consume the budget. Remaining attempts create room to recover. A recovery signal is the key: it says why the next attempt should be different. The score is a teaching device, not a production reliability estimate.
