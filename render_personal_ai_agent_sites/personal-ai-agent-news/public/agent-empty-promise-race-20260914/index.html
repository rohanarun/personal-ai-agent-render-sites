Empty Promise Race

An agent has no eligible workers. Does waiting for the first result mean there is nothing left to do, or nothing that can ever finish?

    Completion needs a candidate

    All of zero tasks have completed, so Promise.all([]) fulfills with an empty array. A race needs one input to settle. With no inputs, Promise.race([]) remains pending.

    const empty = Promise.race([]);
const all = Promise.all([]);
let stop;
const stopSignal = new Promise(resolve => { stop = resolve; });
const guarded = Promise.race([empty, stopSignal]);
// Later, when an explicit stop is requested:
stop('stopped');

    The stop signal settles the outer guarded race. It does not change the original empty race. Here it fulfills with the string "stopped"; production code must distinguish that outcome from a successful worker result.

    Observation is not introspection

    The labels record attached fulfillment callbacks. They are not a synchronous inspection of hidden Promise state. In particular, all([]) is already fulfilled on return, but its callback runs asynchronously. After a zero-delay timer, the page records which callbacks have run; that timer is an observation checkpoint, not a precise duration.

    A finite browser observation alone cannot prove a promise stays pending forever. The empty-race guarantee comes from its API contract. This experiment uses native promises to expose the consequence.

    Define the empty-work policy

    A dispatcher should decide what an empty eligible-worker list means before awaiting a first result: return a documented no-work outcome, reject as a configuration error, or wait for a separately defined signal. A race does not invent this policy. Resolving an outer race also does not cancel underlying work.

    Reset starts a fresh observation and ignores callbacks from the previous run. This page performs no network tasks and sends no model requests.
