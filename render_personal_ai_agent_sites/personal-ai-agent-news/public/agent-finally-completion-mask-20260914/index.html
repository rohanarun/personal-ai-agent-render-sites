Finally can hide a failure

Cleanup ran. That does not mean the task succeeded.

A native try/finally block can change the completion that reaches its caller. This experiment runs the actual statements, catches the final outcome outside the function, and preserves the trace.

    The outer caller sees the replacement
    In the default case, the task throws task-error. The finally block then returns cleanup-result. The caller observes a normal return, not the error. There is no catch inside the function recovering the failed task: its completion was replaced by cleanup's return.
    For an agent wrapper, a success-looking return can hide an unsuccessful tool operation. Treat completion reporting as a contract with the caller, not merely a log line saying that cleanup ran. The trace here is illustrative and performs no real tool action.
    Cleanup has its own failure mode
    When cleanup finishes normally, the pending task return or throw survives. When cleanup throws, that error replaces the task's pending completion. A failing task plus failing cleanup therefore needs a deliberate error-reporting policy if both causes matter.
    Keep resource release separate from claims about task success. If cleanup errors are recorded independently, do not silently discard them; decide which error the caller receives and preserve supporting evidence. A cleanup log is not proof that the underlying resource was released.
    Not the Promise callback rule
    A return statement inside a language-level finally block exits its containing function. By contrast, returning an ordinary value from a Promise.finally callback does not replace the promise's original settled value. Similar names do not make these control-flow contracts interchangeable.
    This page tests synchronous JavaScript only, without process termination, asynchronous cleanup or cancellation. Each run starts a new trace. The export contains the selected statements and observed completion, not a record of a production agent.
