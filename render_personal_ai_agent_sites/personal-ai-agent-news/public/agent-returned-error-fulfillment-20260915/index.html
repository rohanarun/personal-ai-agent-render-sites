Two separate questions
Did the promise fulfill or reject?
An async function returns a promise. Returning a normal Error instance produces a fulfillment value, just like returning other non-thenable objects. An uncaught throw rejects it. Catching a thrown error and returning it converts that path into fulfillment.
The raw branch labels come from actual native fulfillment and rejection handlers attached to the same source promise used by the wrapper. “Fulfilled” describes control flow, not business success.
Does the value satisfy the tool contract?
This wrapper's deliberately narrow contract rejects a returned, same-realm Error instance. The conversion occurs in a fulfillment handler that throws the value. The original source promise remains fulfilled; the new wrapper promise rejects.
Uncheck the contract to see the returned Error continue through both fulfillment paths. A normal success record passes either way. An original rejection passes through the wrapper as rejection.
This guard is not a universal detector
Returning errors as data can be intentional. Use the API's declared result protocol rather than guessing from a message or object name. A production tool might define a tagged result such as an explicit success/failure field instead.
The example does not recognize cross-realm Error instances, serialized error-shaped objects, arbitrary failure records, or failures hidden in successful-looking data. It performs no remote tool call, retry, or action. Don't infer real task completion from either a resolved promise or this local guard alone.
Preserve both observations
The export records the chosen producer behavior, contract setting, and both observed settlements. Error name and message are explicitly serialized as evidence; stack traces and live Error identity are not exported.
