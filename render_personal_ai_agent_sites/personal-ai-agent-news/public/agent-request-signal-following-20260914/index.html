Identity and dependency differ
The request constructor creates a signal that follows the supplied signal. Request.signal === controller.signal is false. Cloning the request creates another signal object; it follows cancellation too. Object identity alone is therefore not a test of whether cancellation will propagate.
Construct first, then abort: the three displayed signals become aborted. Reset, abort first, then construct: the request and clone start already aborted. Their listeners are attached after construction, so their recorded abort-event counts remain zero even though their aborted state is true.
An event count is not current state
This page records listeners attached to each signal and snapshots taken after each action. A listener attached after cancellation does not receive a replay of that event. Check the signal's current aborted state when admitting work; listening only for a future event can miss a stop that already happened.
The fixed string reason is "review-stop". Reset constructs a new controller and new experiment state; it does not turn an aborted signal back into an active one. Each request and clone is created once per experiment.
What an agent can conclude
Illustrative agent scenario: a coordinator passes a signal into a request-building helper. A distinct returned signal does not mean the helper discarded cancellation. Track the relationship through observable state and the API's contract, not reference equality alone.
No fetch occurs here. Creating a Request for the reserved example.invalid address does not send it. These observations demonstrate signal propagation, not server-side rollback, completed-request reversal or cancellation of unrelated tool actions. A remote side effect requires its own confirmation and recovery policy.
