Shared views, separate copies

An agent tool can pass a window into a byte buffer without copying it. A later write can then change another component's input. Explore the difference with real JavaScript typed arrays.

One buffer, two ways to take a window

Illustrative bytes, not a model tensor or production workload. Window: indices 1 through 2.

Source: Uint8Array

View: source.subarray(1, 3)

Copy: source.slice(1, 3)

Try to change only one consumer
Write 99 into shared-view index 0. Source index 1 changes too, because both refer to the same storage location. The copy keeps its original value. Next, write 7 into copy index 0: neither the source nor its view changes.
The view's local index 0 maps to source index 1. Its byte offset is 1 because each Uint8Array element occupies one byte. The end index 3 is exclusive. Reset allocates a new source and recreates both windows.
What this means for agent tools
Illustrative scenario: a parser retains a view while a producer reuses its input buffer. If the producer writes again, the parser can observe changed bytes. Decide who may mutate storage and how long consumers may retain it. A copy separates these particular buffers; it is not a universal concurrency or security guarantee.
This experiment uses ordinary Uint8Array instances and a fixed ArrayBuffer. It does not benchmark allocation, demonstrate SharedArrayBuffer concurrency, or describe the copying behavior of every ML tensor library.
