Partial Assignment

An exception does not mean nothing changed. Apply one patch to a record with a non-writable field and inspect what survives.

Initial values: a = 0, b = 0, c = 0.

No assignment yet.

A patch is a sequence of writes

The source supplies a = 1, b = 2 and c = 3. Initially, b is non-writable. With source order a, b, c, the native Object.assign call reads a and writes 1, then reads b and fails to write 2. The target keeps a = 1. It never reaches c.

Reverse the order: c is now written before the same failure. Put b first and the target stays unchanged. Allow writes to b and every field is updated. Each run constructs fresh source and target objects, so one experiment does not inherit changes from the previous run.

Read traces are not write receipts

Source getters append their field names to the trace. That proves which values were read, not that they were successfully assigned. In the failing run, b appears among reads even though its target value stays zero. The export separates read order, final values, target descriptors and the caught error name.

Only three enumerable, non-integer string keys are used, created in the chosen order. This is not a claim about every possible key order or about objects with proxies and arbitrary side effects. The display reads plain target data properties after the assignment ends.

Agent state needs a commit boundary

Illustrative scenario: an agent updates a task record and catches an exception. Reporting the whole update as simply failed can hide partial state that a retry will encounter. Record the resulting state, not only the exception.

For plain records, validate a candidate state before publishing it through a controlled ownership boundary. Do not assume Object.assign provides a transaction or rollback. Copying into a temporary object also does not undo external effects from getters or setters; those require their own design and recovery policy.
