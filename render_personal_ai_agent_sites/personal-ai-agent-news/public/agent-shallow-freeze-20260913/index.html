Frozen outside. Mutable inside.

An agent's configuration can look locked while a nested object still changes. Explore real Object.freeze behavior with a small, illustrative configuration.

Changing scope starts a fresh experiment. All write attempts run in strict mode.

config.options
    One reference, two objects
    The outer object has a name and an options reference. Freezing that outer object prevents changing those data properties. It does not traverse the options reference and freeze the object at the other end.
    With only the outer object frozen, incrementing options.limit succeeds. Replacing options with a new object fails, because that would write the outer property itself. Changing name also fails. In strict mode these rejected assignments throw TypeError; the experiment catches and records them.
    Freeze the known child, then try again
    In the second mode, this page explicitly freezes options and then config. The same nested write now fails. This is deliberately not a generic deep-freeze implementation: there are only two plain objects, with no cycles, accessors, Map, Set, or class-private state.
    Illustrative agent scenario: two components share an options object. A frozen wrapper does not stop one component from changing the nested limit observed by the other. Decide which component owns mutable state. Freezing is not validation, a security sandbox, or proof that a task respects its limits.
    Reset creates new objects. It does not unfreeze the old ones. The numeric limit here is a demonstration value, not a recommended production policy. No model or external agent is running.
