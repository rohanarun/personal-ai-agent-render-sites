When a field hides reset

A browser agent finds a form and calls form.reset(). The field name can change what that property means.

form.reset();
// Explicit native method, with the form as receiver:
HTMLFormElement.prototype.reset.call(form);
The property lookup changed
Form controls are exposed through named access on their owner form. A control with name or ID reset can mask the reset method. Here the property resolves to an input element instead of a function; calling it throws a TypeError. The explicit prototype call avoids that named lookup in this same-realm demonstration.
The second button is not another reset implementation. It invokes the native form method with the correct receiver. The reset-event counter records whether that event fired, and the before/after values show whether the edited draft returned to its default. Error text may vary across browsers.
Reset is not erase
Reset restores default field values, which can be nonempty. It does not mean every field becomes blank, nor does it reset every attribute such as disabled. In this experiment no listener cancels the reset event. A page that prevents that event can stop the default reset behavior, so an event alone is not proof that a field changed.
For an agent maintaining a form tool, inspect the resolved property and verify the intended value afterward. Avoid naming controls after native form members in interfaces you own. On unfamiliar pages, use explicit element references and preserve user data until the requested reset is authorized. This sandbox contains only a local draft; nothing is submitted or sent to a model.
