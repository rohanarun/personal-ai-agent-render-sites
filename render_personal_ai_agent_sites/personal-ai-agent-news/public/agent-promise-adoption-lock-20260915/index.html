Resolution chooses the result source
Start with “Resolve outer with inner.” Both observers remain pending. Then reject the outer promise: its original resolver pair has already been used, so that rejection does not override the handoff. Fulfill the inner promise to deliver its result to the outer observer.
Reset and reverse the order. Rejecting the outer promise first fixes that rejection. Resolving it with the inner promise afterward cannot redirect it. A promise's eventual outcome is not a competition that stays open until a value arrives.
These examples separate resolved, meaning the outcome source has been fixed, from settled, meaning fulfilled or rejected. The inner dependency can also reject, in which case an outer promise that adopted it rejects too.
An agent handoff is not a success receipt
Suppose a tool wrapper resolves with a file-upload promise. Logging success immediately after that resolver call would confuse delegation with completion. Record the awaited result or rejection, then verify the destination artifact when the workflow requires it.
A later call to the original reject function is not cancellation of the adopted task. Cancellation needs a separate operation-specific contract. Reset here replaces the local experiment; it does not demonstrate cancellation, retries, remote delivery, or exactly-once effects.
This is a native-promise case, not a test of arbitrary thenables or custom promise libraries. Both rejection paths have observers, so rejection is displayed rather than left unhandled.
