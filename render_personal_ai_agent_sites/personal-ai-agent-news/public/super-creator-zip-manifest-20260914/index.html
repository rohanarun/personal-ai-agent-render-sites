    Names before extraction

    A designer receiving a logo package can check whether the expected source, preview and usage-note names appear. The synthetic example contains those categories, not real client assets. A filename alone cannot establish that an asset is correct, licensed or even the type its extension suggests.

    This desk uses JSZip 3.10.1 to load the archive's entry map. It does not request decompressed entry contents or perform CRC32 validation. Password-protected and multi-volume archives are unsupported. A parse success does not prove integrity.

    JSZip normalizes relative parent-path components and exposes original file names where available. The manifest records both. Duplicate names can collapse in the library's entry map, so this is not a forensic inventory of every raw ZIP record. Legacy filename encoding can also be ambiguous.

    There is no extraction, malware scan or safe-path certification here. Use trusted sample archives; the file-size cap is a usability limit, not a defense against every hostile archive. Large entry maps can still consume browser resources. This desk accepts up to 2,000 loaded entries.

    Owner and task/source context are required for lookup. Missing context, no entries or no safe match returns a miss; the caller must handle it. A miss is not completion, and matching may incur model usage. Eligible procedure reuse can avoid rebuilding steps, but source inspection does not prove measured savings, universal app support or availability for your account.

    For a pilot, inventory a synthetic package, compare the manifest against a human-approved expected list, and stop before any upload or replacement of production assets. Keep content inspection and publishing approval separate from the filename check.
