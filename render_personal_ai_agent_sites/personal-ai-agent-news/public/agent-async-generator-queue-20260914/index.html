Requests are not parallel bodies

An async generator's next method returns a promise for an iteration result. In this native fixture, three calls request successive results from one generator. The first pause holds the sequence; queued reads do not skip past it. After both pauses are released, the results are A, B, then finished with done true.

The two yield results have done false. The final value is a return value, not another yielded item. These results are actual browser observations. The async-generator next reference demonstrates queued calls and the iteration-result shape.

What an agent consumer can infer

Imagine an adapter exposes an ordered stream of local progress records. Calling next repeatedly is a request to consume that stream, not evidence that several independent workers were started. A pending read should not be reported as completed work.

This fixture chooses to create its pauses before reading, and advances a single body around them. Real work launched elsewhere might run concurrently. Do not generalize the result into a claim that all operations behind every async iterator are serialized. Check where those operations are created and what the iterator actually controls.

Queue size also deserves a contract. A consumer that keeps requesting results can build up demand without increasing useful throughput. Decide how many reads may be outstanding and how cancellation is handled by the actual producer. This lab does not implement a production backpressure policy.

Reset is fixture cleanup

Reset releases any old local pauses, discards the visible run, and ignores its later callbacks. It does not demonstrate cancellation of external work. No external work exists here. The export is enabled only after all three promises settle and contains their caller indexes, values and done flags.
