Why does updating one task's state sometimes change the whole batch?

Values and reference identity

Native JavaScript arrays and objects. Reference IDs are local labels, not memory addresses. Changing mode or resetting rebuilds the example. No agent work runs.
Follow the shared reference
In fill mode, all three slots reference the same object. Incrementing its attempts through any slot changes the object seen through every slot. The array contains three entries, not three independent objects.
Replace slot 1, then increment it. That assignment installs a new object only in slot 1; slots 0 and 2 still share their original object. The reference labels expose the split even when values happen to match.
A factory must create something new
The Array.from example creates a new object on each callback invocation. Merely using a callback is not enough: returning one preexisting object would still share it. A fresh outer object can also contain shared nested objects.

Inspect identity before debugging the agent
Illustrative batch-runner failure: several task cards show the same retry count because their state records share an object. That symptom need not mean multiple requests ran. Check initialization and identity separately from execution logs.
This lab isolates in-memory references. It does not model concurrency, retries, persistence, or distributed ownership. Its JSON export records identity labels explicitly because repeated JSON values alone do not preserve shared references.
