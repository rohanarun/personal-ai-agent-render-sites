Super Powers AI vs GitBook for small software teams: separate the place you publish a procedure from the evidence that it still works.

Short answer: choose GitBook when you need a documentation home. Evaluate Super for a bounded research or browser-checking task around that home. Do not replace a docs platform with an agent just because both can write.

What you are actually choosing

GitBook offers a visual editor, GitHub/GitLab sync and preview deployments. Its current product also includes agent-oriented knowledge features; this is not a comparison between an AI product and a passive text editor.

Super advertises cloud browsers, apps and research reports. A proposed use here is gathering observations and drafting a discrepancy report. This article does not demonstrate a shipping GitBook connector, authenticated test runner or automatic docs update.

How to refresh a guide without rewriting blindly

Imagine your guide says “open Settings, select API keys, then create a key.” A release moves the entry point to Workspace settings. A fluent rewrite can still preserve the wrong location. The unit of review should be a claim plus an observation, not a polished paragraph.

  1. Freeze the scope. Select one guide and record its revision, target product version, account role and expected outcome. A viewer account is not a valid test of an administrator-only path.
  2. Observe before drafting. In an authorized test environment, record the visible label and a timestamp. Stop before creating credentials, sending messages or changing billing. Redact identifiers and secrets from evidence.
  3. Separate differences from guesses. Report “API keys appears under Workspace settings in this test account.” Do not generalize that to every plan or claim a backend permission change.
  4. Prepare a narrow proposal. Include the old instruction, observed replacement, evidence reference, tested context and unresolved questions. Keep the existing guide intact while the owner reviews.
  5. Publish and replay. A human owner accepts the change in the docs workflow. Re-run the exact reader path after publication and verify the public page, not only the draft.

Prerequisites: an owner for the guide, permission to inspect the application, an appropriate test account, and a place to retain redacted evidence. Without those, ask for access or report uncertainty. Do not let an agent improvise permissions.

What evidence permits an update?

This fictional review exercise uses a deliberately conservative local policy. It does not inspect your application or constitute a GitBook feature.

Claim: “Every user can create an API key from Settings.”

Why an administrator test is not enough

The word “every” includes roles you have not tested. Narrow the claim to the observed role, or collect evidence for the other roles. An approving owner cannot manufacture missing observations.

When to keep the old text temporarily

If the discrepancy is unverified, retain it as an open issue rather than silently substituting a guess. If the old instruction could cause harm, the owner should consider a warning or withdrawal while investigating.

A cache hit is not a fresh observation

Super's public computer-use-cache repository is concrete inspectable technology. The pinned server implementation uses normalized request keys and stores eligible responses. A hit can avoid an upstream model request; misses go upstream, with TTL and bypass controls affecting reuse. Streaming misses are not stored by this implementation.

That proves a reuse mechanism, not that a browser was revisited. Put fresh observations in the review evidence and use bypass or invalidation where appropriate. Neither a cached response nor a newly generated answer proves a button exists today. Public code also does not establish every production configuration or a measured saving for this task.

Who should choose what?

Choose GitBook first when your missing capability is publishing, organizing and collaborating on docs. Evaluate its native AI and existing workflow before adding another tool. Consider a small Super trial when the bottleneck is gathering scattered, authorized evidence outside the docs, and a human can verify the result. Use neither as proof of correctness: a repeatable application test and a accountable reviewer remain separate responsibilities.

Success for a trial is one accepted, evidence-backed correction and a replay that reaches the intended outcome. Measure review time and rejected suggestions too. If supervision takes longer than doing the check directly, keep the manual workflow.
