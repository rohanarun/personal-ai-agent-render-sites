One float, two byte orders

A binary tensor needs a format contract. Four bytes alone do not tell a reader which end comes first.

Change the interpretation, not the bytes
The two readings use the same buffer. DataView.getFloat32 receives an explicit littleEndian flag for each interpretation. The hexadecimal strip is memory order from left to right, not a decimal number written in four pieces.
Why this matters for ML
Illustrative scenario: a custom loader reads raw float32 tensor bytes produced elsewhere. If its byte order disagrees with the writer, a plausible input can become a tiny value or something else entirely. Consult the actual file-format specification; this page does not decode a model checkpoint.
Byte order is only one part of the contract. Shape, data type, offsets, layout and any quantization metadata also matter. A successful parse does not establish that a tensor is meaningful or a model is correct.
Special values are not ordinary numbers
Negative zero, infinity and NaN are shown as strings in the exported report so JSON does not silently replace or erase their distinction. This is an interpretation report, not a lossless floating-point file format. The original byte list is retained.
