A fixed link is not a frozen parent
The setup is parent = {limit: 3}, followed by config = Object.preventExtensions(Object.create(parent)). Config has no own limit. Its read follows the existing prototype link.
Why the two writes differ
Writing limit on config would create an own property, which this object forbids. Changing parent.limit edits an existing property of another, still-mutable object. The next config.limit read observes that updated inherited value. The failed own write does not modify the parent.
Why the same prototype succeeds
Reflect.setPrototypeOf returns true when asked to preserve the exact existing prototype. A different object, even one containing the same limit, is a different identity and is rejected here. The operation returns a boolean; this experiment does not use the throwing Object.setPrototypeOf variant.
What an agent should validate
Imagine a wrapper treating non-extensibility as proof that a tool's limit cannot change. This local counterexample breaks that assumption without adding a key. Decide whether a setting must be an own property, snapshot validated primitive values at the consuming boundary, and control all objects that can influence a read. None of these object flags is an authorization boundary for untrusted code.
This is an ordinary-object experiment. It does not model proxies, accessors, remote services or a running Super account. Exported snapshots include the observed inherited value, own-property test, prototype identity and each native return value.
