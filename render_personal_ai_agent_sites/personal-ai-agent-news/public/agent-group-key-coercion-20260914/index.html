Grouping keys

A bucket name and an identity are not the same contract.

      When a dispatch queue merges

      Suppose a tool batch is grouped by a caller-provided tenant label. The number 7 and string "7" remain different Map keys, but both become the property key "7" in Object.groupBy. That can merge intended destinations if the adapter accepts both types.

      This is an illustrative routing hazard, not an authorization system. A Map is not a security boundary either. Validate identifiers at admission and choose a key contract shared by the producer, batcher and consumer. If identifiers should be strings, normalize and validate them explicitly rather than relying on incidental coercion.

      Objects collapse; symbols do not

      In the object case, A and B are distinct plain objects. A appears twice. Native Object.groupBy converts both objects to the same ordinary string representation; Map.groupBy retains two identity groups. Structurally identical objects do not become equal Map keys.

      The symbol case is a useful counterexample: two Symbol("team") values remain distinct keys in both results. Object.groupBy preserves symbol keys; it does not stringify them. This page enumerates object groups with Reflect.ownKeys, so symbol groups are visible.

      The object result has a null prototype. That avoids inherited object methods, but does not undo key coercion. Use a deliberate enumeration method rather than expecting result.hasOwnProperty to exist.

      An export is an observation, not a live Map

      The JSON export uses explicit key types and local identity labels. Labels A and B identify objects or symbols only within this run; importing that JSON cannot recreate the original identity. No raw Map serialization or symbol omission is disguised as a faithful copy.

      Group arrays contain the original records, not deep copies. The diagram shows membership only, not isolation, scheduling or concurrency. No agent or model request is made.

      Primary references: Object.groupBy and Map.groupBy. Native support is required; an unavailable method is reported rather than simulated.
