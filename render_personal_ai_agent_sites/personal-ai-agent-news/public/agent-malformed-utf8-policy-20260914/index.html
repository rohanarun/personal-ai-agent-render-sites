An agent can receive bytes that are not valid text. A readable result is not proof that decoding preserved the original data. Compare two real browser decoders on one complete byte sequence.

Same bytes. Different failure contract.
Default UTF-8 decoding substitutes malformed sequences with U+FFFD. Fatal decoding throws a TypeError instead of returning a string for that call. The displayed output and error below come from your browser, not a simulated decoder.
A replacement glyph does not prove corruption
The valid bytes EF BF BD encode U+FFFD itself. Both decoders accept them. Counting replacement characters in an already decoded string cannot distinguish intentional characters from decoder substitutions.
Where this matters in an agent pipeline
An illustrative ingestion adapter may reject malformed text before parsing a tool response, or accept replacement for a best-effort preview while retaining the original bytes. Choose that contract explicitly. Fatal decoding validates this encoding, not the truth, safety or schema of a tool result.
Complete input, not streaming
Each run creates two fresh TextDecoder instances and calls decode without stream:true. An unfinished final sequence is therefore malformed here. A streaming decoder can retain partial bytes for a later chunk; that is a separate boundary problem. The default UTF-8 BOM handling is unchanged.
This local experiment accepts zero to 256 bytes, each written as exactly two hex digits. No model calls, remote tool execution or file uploads occur. The export records bytes, output code points and caught errors, not a remote service guarantee.
