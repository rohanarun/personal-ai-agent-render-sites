Queued Destination Lab

A queued function can read tomorrow's state. Does your agent job mean the destination at enqueue time, or the destination at execution time?

No jobs queued.

let destination = 'Drafts';
const liveJob = () => destination;
const captured = destination;
const snapshotJob = () => captured;
destination = 'Review';
// liveJob() -> Review; snapshotJob() -> Drafts

The binding is not a frozen value

A closure keeps access to its lexical environment. The live-policy function reads one shared destination binding at invocation. The snapshot policy creates a new local binding for each job, holding the string selected at enqueue time.

Try queueing one job with each policy while Drafts is selected. Switch to Review, then run both. Their enqueue records agree but their results differ. Changing the policy affects only future jobs; changing the destination affects already-queued live jobs. Each callback here executes real native JavaScript.

Make temporal intent explicit

Neither policy is universally correct. An immutable recipient decision may need enqueue-time data; a dashboard refresh may intentionally read current state. A captured object would still be a reference to that object, not a deep snapshot. This demonstration uses primitive strings to isolate binding behavior.

The queue is fictional: no files move, no agent runs and no network action is dispatched. It executes FIFO only when you press Run next job. There are no timers, retries, persistence or authorization checks. A maximum of 12 jobs keeps the entire ledger inspectable; reset starts a fresh experiment.
