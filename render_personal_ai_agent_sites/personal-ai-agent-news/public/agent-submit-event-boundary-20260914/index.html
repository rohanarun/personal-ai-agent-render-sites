A Submit Event Is Not a Submission

An agent can trigger an event listener without passing the browser's form checks. Compare three actions on the same required field. The trace below records actual native events, not a simulated result.

Field validity: missing required value.

A valid field and a fired submit event are different observations. Neither proves that a server accepted or saved anything.

Exact synthetic operation

form.dispatchEvent(new SubmitEvent('submit', {
  bubbles: true,
  cancelable: true,
  submitter: button
}));

Even supplying the same submitter does not initiate constraint validation. This listener cancels the event, so dispatchEvent returns false. That false means cancellation, not a failed network request.

What should an agent verify?

A handler ran. A form passed validation. A server stored a record. These are three different claims.

Empty subject: a useful counterexample

With the bypass checkbox off, button activation or requestSubmit(button) encounters the required field and produces an invalid event, not a submit event. A manually dispatched SubmitEvent reaches this listener even while the field is invalid. Filling the subject makes both native submission paths reach the listener.

Bypassing checks is explicit

The checkbox changes the submit button's formNoValidate property. Both native paths honor that button setting. It does not change the field's validity and does not authorize an operation. Server-side checks are still necessary. This page does not call the separate form.submit() method, which skips both constraint validation and the submit event.

A recorded click is not a completion receipt

Illustrative agent task: send a support request. A test that only waits for a submit callback could pass on the synthetic path with an empty subject. A browser workflow should exercise the intended control, observe validation failures, and verify the destination's actual result before claiming completion. This experiment deliberately cancels all submissions, so it can never provide that final proof.

What the trace does and does not show

The validity snapshot reads input.validity.valid; it does not call checkValidity(), which could add extra invalid events. Each action starts a fresh trace. Editing the field or bypass setting clears the old result. isTrusted and submitter are recorded as browser observations, not as an authorization policy. Other pages can have custom listeners, extra constraints, or framework behavior not represented here.
