The extra argument changes the meaning

map calls its callback with the element, index and array. parseInt uses its second argument as a radix and ignores the third. With three "10" strings, the direct call uses radix 0, then 1, then 2. Those yield 10, NaN and 2. The default inference at radix zero is not the same as interpreting every index as decimal.

values.map(parseInt)
values.map(text => parseInt(text, 10))

The wrapper deliberately supplies radix 10 and ignores map's extra arguments. It returns 10 for all three default entries. Rearranging a batch should not silently change a field's intended numeric base.

Parsing is still not validation

The decimal wrapper fixes the callback mismatch, but parseInt accepts a numeric prefix. Try "12px" or "1.9": the wrapper returns 12 and 1. If an agent's input contract requires a complete integer string, a successful prefix parse is not enough.

Choose and enforce the accepted input grammar before using the value. This experiment does not claim that every finite result is a valid identifier, count or safe integer. The source array is a dense list of strings, so blank lines are actual entries rather than missing array slots.

Make adapter boundaries explicit

Illustrative agent pipeline: a tool returns text fields and a batch adapter converts them. Passing a function by reference can be convenient, but its optional parameters may have meanings unrelated to the callback API. Inspect both signatures, then write an adapter that names the intended conversion.

The results use native map and parseInt. Exports tag NaN and negative zero explicitly rather than letting JSON turn NaN into null or erase the sign of zero. The file includes the entered strings; keep examples free of secrets.
